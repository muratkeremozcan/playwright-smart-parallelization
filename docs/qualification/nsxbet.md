# NSXBet playwright-orchestrator qualification

Verdict: does not qualify.

`@nsxbet/playwright-orchestrator` assigns single tests from historical durations. It has no notion of a Playwright project, a serial group or a repeat, and its timing history has no guard. Driven the way its README describes, it runs tests in more than one shard and splits serial groups, and it splits them under every file-affinity setting it offers (proofs 1 and 2). Its `merge-timing` accepts a missing shard artifact with exit code 0 (proof 6), and it replaces history from failed and cancelled runs and from a damaged history file (proof 8). A delayed run overwrites a newer one (case X2). A shim, `qualification/nsxbet/shim.js`, closes the failures of proofs 1 and 2 on the fixture (rows `1.grouped-repeat-each` and `2.grouped-*`). The failures of proofs 6 and 8 have no shim, because they happen inside `merge-timing` and `extract-timing`.

The rows below come from `npm run qualify:nsxbet`. The tests in `qualification/nsxbet/tests` assert every result in this document, and `tests/unit/docs.test.js` fails when the verdict, a proof result, a row result or a generated table disagrees with the evidence.

The package's composite Actions were not run. Their source at the `v2` tag of `NSXBet/test-orchestrator` (commit `54c22bb65fa27872bc76266e48d9d50c277e9d79`) shows `setup-orchestrator` installing the latest npm version, `orchestrate` setting `use-orchestrator=false` for the whole run when `assign` exits non-zero or prints no JSON (so every `get-shard` returns `--shard=N/M`), and `extract-timing` and `merge-timing` ending with exit code 0 and a warning when the CLI fails.

## How the engine was driven

Every run goes through the S2 harness: the engine's output becomes a per-shard `--test-list` partition, the harness runs each shard with a reporter that records the leaves it executed, and its checks decide exactly-once coverage, execution outcomes (a skipped test fails the run), serial integrity and dependency accounting. A partition that hands Playwright a `--test-list` is also held to the harness selection contract: the engine plans with title-path prefix lines, which Playwright reads as described in [docs/playwright-test-list-selection-limits.md](../playwright-test-list-selection-limits.md). The fixture meets that contract, so no row below changes because of it, except `1.prefix-titles`. The timing input is built from the Playwright JSON reports of a native two-shard run: `extract-timing` per project and shard, then `merge-timing`. Durations in that history are rounded to 50 ms, so the assignment does not depend on a few milliseconds of run-to-run noise. Runs use four workers, except the runs that feed the balance table (`2.history`, `2.grouped-history-2`, `2.grouped-history-3` and the native baselines), which use one worker per shard.

| Flow     | What it does                                                                                                                                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| combined | One `--list` of the whole config, one `assign`, one `--test-list` file per shard. This is the package Quick Start applied to a config with two browser projects.                                                             |
| jobs     | One list, one `assign` and one set of jobs per project, `--project` on every job. The package documents `--project` for multi-project configs.                                                                               |
| merged   | One `assign` per project; the shard lists of all projects are merged into one file per shard, each line prefixed with `[project] ›`. A shard keeps running every project in one Playwright invocation, like native sharding. |
| grouped  | `merged` with one `assign` for all projects through the shim: files carry their project, a serial group is one test, a test repeated by `--repeat-each` is listed once.                                                      |

## Serial groups and file affinity

File affinity is a soft cost: the engine adds a penalty when a file's tests land on different shards. With no history every test is estimated at 30 seconds and the penalty is 30 seconds; with history the penalty is the 25th percentile of per-file averages. The rows `2.cold`, `2.history`, `2.no-affinity` and `2.huge-penalty` show that the setting changes which groups split and leaves some group split every time. The engine balances single tests, so a serial group of five tests is spread like any five tests unless affinity pulls them together. A split is visible when the second test of a serial pair runs without the first: its shard fails.

## Privacy

The plan and timing steps make no outbound connection. Two independent checks cover them. A preload (`qualification/lib/net-guard.js`) records and refuses every socket, DNS lookup and `fetch` in the process and its Node children, and records every process the engine spawns; its control row shows it catches each kind, and the mutation control row shows a spawned `curl` fails the check. The same steps also ran under an OS-level network block, after the block was shown to stop a connection to a local listener. Both ran for cold and warm `assign`, `extract-timing` and `merge-timing`.

## Smallest remaining integration gap

The Action needs three pieces around the engine.

1. Project and serial-group handling in front of `assign`: namespace files with their project, hand a serial group over as one weighted test, list a repeated test once, then expand the result into `[project] ›` lines. `shim.js` does this, and rows `1.grouped-repeat-each` and `2.grouped-*` show it covers every leaf once and keeps every group whole on the fixture.
2. A history guard around `assign`, `extract-timing` and `merge-timing`: validate the history before `assign` (rows `5.truncated`, `5.string-durations` and `5.zero-durations` show the engine accepts damaged history without a warning) and every input and the existing history before merging, merge only from complete successful runs, and publish through one writer that rejects an older run. Rows `x1.damaged-shard-artifact`, `6.missing-timing-artifact`, `8.damaged-history`, `8.failed-run`, `8.cancelled-run` and `x2.racing-publish` reproduce each failure this guard must stop.
3. A completeness check of shard artifacts before aggregation, because both `merge-reports` and `merge-timing` accept fewer shards than ran (`6.missing-blob`, `6.missing-timing-artifact`).

The assignment depends on the time the search was given (`4.single-assignment`), so it is computed once and distributed to the shards, as the package README describes. Planning in each shard breaks coverage (`x1.recompute-per-shard`).

## Reproduce

```sh
npm run qualify:install
npm run qualify:nsxbet
npm run qualify:nsxbet:test
```

`qualify:nsxbet` writes `qualification/nsxbet/evidence.json`; `--group coverage|serial|assignment|history|privacy` collects one group, and `--merge FILE...` joins the evidence of the groups. The `Qualification` workflow runs the five groups on separate runners and merges them before asserting. `qualify:nsxbet:test` asserts every result; with `PSP_NSX_EVIDENCE=FILE` it reads an evidence file instead of collecting again. The reference evidence behind this document is `docs/qualification/nsxbet-evidence.json`.
