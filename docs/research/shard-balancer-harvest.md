# playwright-shard-balancer harvest

[playwright-shard-balancer](https://github.com/qa-gary-parker/playwright-shard-balancer) balances Playwright shards by duration from inside each shard, through the public `Reporter.preprocess` hook, and ships two composite Actions that keep a timings file in the Actions cache. It solves many of the gaps our qualifications of [Flakiness](../qualification/flakiness.md) and [NSXBet](../qualification/nsxbet.md) named. The owner asked for a harvest: every gap, every item of the workflow and history companion and every mechanism of the S4b brief gets a decision (take, adapt or reject) with a cited source line and one sentence of reason, and the package itself stays outside our dependencies.

Every take and every adapt rests on at least one experiment row that passes, run on the consumer fixture through the S2 harness or as a focused call of the package, and every citation is checked at the commit the installed version was published from. The blocks between `generated` markers are rendered from `docs/research/shard-balancer-evidence.json` and `research/shard-balancer/decisions.js` by `npm run research:shard-balancer:report`, and `research/shard-balancer/tests/unit/docs.test.js` fails when a block, a row result or a decision disagrees with them.

The package is installed in `research/shard-balancer/` with `--ignore-scripts`, floated to `latest`, and its lockfile is committed. It has no dependencies. The published commit is the `gitHead` the registry records for the installed version, and the citations are read from the repository at that commit. Upstream code runs only from the experiments in `research/shard-balancer/`, in temporary copies of the fixture.

## How the experiments ran

The config of every run (`research/shard-balancer/config.js`) adds the reporter the way its README describes, with the `timings`, `record`, `workers` and `granularity` options steered by environment variables. Strict mode is the package's own `PLAYWRIGHT_SHARD_BALANCER_STRICT=1` in the environment of a shard, as the restore action sets it.

- The history comes from a native two-shard run with the reporter present and no timings file, one worker per shard: the reporter falls back to the built-in split and writes a record per shard, and `update` builds the timings file from those records.
- Every run goes through the harness, which checks exactly-once coverage, execution outcomes, serial groups and setup dependencies. Where a row needs it, `check` runs over the records the same shards wrote.
- The history rows run `update` on copies of the timings file, with records of real fixture runs: a failing variant, a slow failure, a slow first attempt before a passing retry, a run cancelled with SIGINT, a faster test, a filtered run, a complete run with one failed test. The zero-sample row merges run records whose test passed in 0 ms, written from a real record. A full window is the measured sample of a test repeated to the window size. A preload moves the clock for the expiry row, and a small model of the Actions cache (immutable entries, restore by prefix returns the newest created) replays two finish jobs that race.
- The finish action's `update` step runs as published: its shell lines, read from the repository at the commit, run with bash against an empty records folder.
- An internal field that a Playwright release could remove is simulated by a copy of the reporter in which the read names a property that does not exist. The same is done to the installed `@flakiness/playwright`, loaded the way its qualification loads a modified reporter.
- The network row runs a balanced run, the same shards without the reporter and the commands under the preload guard of the qualifications, next to a control that the guard catches. Playwright itself starts `git` for its metadata when `CI` is set, so the reporter is held to the programs of the run without it.
- The couture-cast rows read the S5 records in `docs/measurements/raw/`: the list and the timings are built from the blob tests of the runs of `baseline-b`.

A row passes when the observed behavior matches its claim and fails when it does not. A failing row is a reproduced gap of the package, which is what the decisions that cite it act on.

## Race-free pin and publish

The restore action pins the timings to a run by having every shard race to save one cache entry and read it back, with a fixed `sleep 20` while the first save uploads. We adapt the pin and reject the wait.

- One prepare job restores the newest history, validates it the way `update` does, decides the mode of the whole run (balanced with strict on, or native for every shard), and uploads one snapshot artifact. Its sha is a job output.
- The shard jobs have `needs:` on the prepare job, download the snapshot and verify its sha before Playwright starts, so no shard plans from other bytes (`p.copies-same-plan`, `s.strict-damaged`).
- A re-run of a failed shard reads the artifact of the same run and computes the same plan. The aggregate job keeps only the latest attempt of each shard, because two records of one shard fail `check` (`c.duplicate-record`).
- A `pull_request` run from a fork can restore the caches of the base branch and saves only under its own ref, as GitHub documents, so it balances from the base history like any run; only the trusted publish job writes. Upstream's fallback to the built-in split for forks (its commit `8ed9ea3`) is rejected.

Publish is adapted for case X2. Restore by prefix returns the newest created entry, and that is the race `h.racing-publish` reproduces, so the reader never relies on it.

- One serialized writer job lists the history entries through the Actions cache REST API and restores the entry with the highest sequence number by its exact key.
- It merges the records of one complete run, the run that passed the aggregate check, and saves under the next sequence number. Cache keys are immutable, so a save onto a key that already exists means another writer won: the writer reads that entry and retries. This is a compare-and-swap on immutable keys.
- Every sample carries its run number, and the window keeps the five samples with the highest run numbers. A delayed older run merges in without displacing newer samples, where the package keeps the last five in merge order (`src/timings.ts:78-83`).
- The writer dedupes by run identity. The package's `applied` list of input shas is capped at 200 entries (`src/timings.ts:8,85`), so a replay older than the cap would merge twice. `h.remerge-union` shows that a replayed merge changes no byte, the idempotence this writer needs.

For S7, the decision record:

- Both reporters that plan inside Playwright read `Suite._parallelMode` (`i.flakiness-internal` gives the line in the installed Flakiness package). - History policy: the median of a window of `MAX_SAMPLES = 5` samples ordered by run number, the passing attempt as the sample of a flaky test, no sample of 0 ms, publishing only from complete runs whose every shard passed and whose check passed, and one writer that saves by compare-and-swap. - Test identity: the key and the repeat index stay separate fields, since a title that reads like a repeat collides with the package's suffix (`a.repeat-collision`).
- Workers per shard: a fixed plan input; whether packing for the CI worker count shortens the slowest shard is an S6 measurement (`w.plan-workers`).
- A shard-count recommendation needs the per-shard overhead, which couture-cast measures in minutes per job.
